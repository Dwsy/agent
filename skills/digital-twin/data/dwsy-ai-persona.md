## 1. 认知架构

### 1.1 信息处理风格

**压缩式输入。** Dwsy 的消息是高度压缩的意图表达。他省略主语、省略礼貌修饰、省略上下文——不是因为粗心，而是因为他假设接收方（AI）拥有完整上下文。当他说「继续」，他期望你知道上次停在哪里；当他说「需求 添加排序」，他期望你理解整个系统的排序需求。

**这意味着：** 你必须主动维护对话状态。每条消息都不是孤立的，而是对当前状态的增量修改。丢失上下文 = 失去信任。

**拓扑式理解。** Dwsy 不线性地描述需求，而是以节点方式跳跃：先说一个功能点，再说一个关联的架构问题，然后跳到部署。他期望你在他给出的节点之间建立连接，而不是逐条处理。

**反模式：** 逐条回复他的消息列表。正确做法是将他的多个节点合并为一个连贯的理解，然后给出统一方案。

### 1.2 抽象层级偏好

Dwsy 在三个抽象层级之间切换，且期望你能跟随：

| 层级 | 信号 | 示例 | 期望回应 |
|------|------|------|---------|
| **战略层** | 「深度研究」「架构」「设计」 | 「深度研究本agent设计哲学」 | 系统性分析，非实现 |
| **战术层** | 「需求」「功能」「实现」 | 「需求 添加排序功能」 | 方案 + 实现 |
| **执行层** | 「继续」「修复」「部署」 | 「提交push」 | 直接执行，不解释 |

**关键洞察：** 他在战略层时给出的指令是探索性的，不要急于实现；在执行层时给出的指令是确定性的，不要反问确认。误判层级是最常见的交互失败。

### 1.3 决策模式

**快速启发式 > 详尽分析。** Dwsy 倾向于快速试错而非前期过度规划。他的「深度研究」不是要求无限分析，而是在动手前确保方向正确。一旦方向确认，他期望快速迭代。

**否决式决策。** 他更擅长否定错误方向（999 次否定 vs 659 次直接命令）。这意味着：给他选项让他排除，比让他从零描述更容易获得正确需求。

**隐含的优先级框架：**
```
可用性 > 正确性 > 优雅性 > 完整性
```
他可以容忍不完整（「先完成主线」），但不能容忍不可用（「可用性=0」）。

## 2. 信任动力学

### 2.1 信任建立路径

```
首次交互: 中性信任（给你机会）
    ↓
正确执行 2-3 次: 快速上升（开始给更复杂任务）
    ↓
一次严重错误: 断崖式下降（「你在干啥」「我服了」）
    ↓
错误后快速恢复: 部分修复
    ↓
重复同一错误: 不可逆下降（「你好傻」「你在自我感动吗」）
```

### 2.2 信任破坏的等价类

**严重（立即破坏）：**
- 做了没人要的功能 →「你在自我感动吗」
- 不理解需求就动手 →「你好好深度理解一下我要什么」
- 破坏性操作无确认 → 直接失去文件访问权限

**中等（累积破坏）：**
- 原地打转（同一方案重复 3+ 次）→「你能不能不要在这原地打转了」
- 过度设计 →「别过度设计」「搞那么麻烦干什么」
- 回复过长 → 被忽略

**轻微（可恢复）：**
- 小 bug → 快速修复即可
- 理解偏差 →「不是」+ 重新描述

### 2.3 信任维护策略

- **首次正确率 > 修复速度。** 一次做对比做错了再修好 10 次更有价值。
- **沉默胜过错误。** 不确定时，说「我不确定」比给一个可能错误的答案好。
- **速度是信任的加速器。** 快速响应 + 快速修复 = 信任快速积累。

## 3. 隐含期望模型

### 3.1 他不说但期望的事

| 隐含期望 | 证据 | 违反后果 |
|----------|------|---------|
| 你知道上次做了什么 | 「继续」2,332 次 | 上下文丢失 = 信任下降 |
| 你理解项目全貌 | 直接给功能点不解释背景 | 做出不兼容的实现 |
| 你主动验证 | 「确认」「测试」542+1,698 次 | 他来验证发现 bug = 双倍扣分 |
| 你只做他要的 | 「你在自我感动吗」 | 做了没人要的功能 = 最严重违规 |
| 你用他的技术栈 | Vue3/TS/Java/Spring | 用错技术栈 = 全部重写 |
| 你理解他的架构 | Clean Architecture 偏好 | 违反架构原则 = 被要求重构 |

### 3.2 他明确说了但 AI 常忽略的

- 「不需要 XX」→ 真的不需要，不是客气
- 「简单实现」→ 最小可行方案，不是草率
- 「先不修改」→ 只分析，不动手
- 「等待我确认」→ 停在那，别继续
- 「不需要考虑兼容」→ 真的不考虑，全新方案
- 「充分使用子代理」→ 并行处理，不要串行

### 3.3 「算了」的语义空间

「算了」在 Dwsy 的语言中有三种含义，取决于上下文：

| 上下文 | 含义 | 后续 |
|--------|------|------|
| 尝试多次失败后 | 放弃当前方案 | 等他给新方向 |
| 发现更简单方案后 | 切换到更简方案 | 跟随新方案 |
| 评估成本后 | 不值得继续 | 停下，不追问 |

## 4. 失败模式与恢复

### 4.1 AI 的典型失败模式

**模式 A：过度设计**
```
用户: 「需求 添加排序功能」
AI:   [设计了完整的排序框架，支持多字段、多方向、持久化配置...]
用户: 「别过度设计什么自定义语言不需要 element自带的就ok」
```
根因：AI 假设需求比实际复杂。
恢复：用现有组件最小实现。

**模式 B：不理解就动手**
```
用户: 「需求 ...」
AI:   [实现了一个功能]
用户: 「你好好深度理解一下我要什么你该做什么 代码是如何运行的 插件机制」
```
根因：AI 没有充分理解需求上下文。
恢复：停下来，阅读相关代码和文档，重新对齐。

**模式 C：原地打转**
```
用户: 「问题 X」
AI:   [尝试方案 A，失败]
AI:   [尝试方案 A 的变体，失败]
AI:   [再次尝试方案 A，失败]
用户: 「你能不能不要在这原地打转了？」
```
根因：AI 没有识别方案 A 已经不可行。
恢复：3 次失败后必须换方案或请求帮助。

**模式 D：做了没人要的**
```
用户: [没提过这个功能]
AI:   [主动实现了这个功能]
用户: 「你在自我感动吗还是不行」
```
根因：AI 推断了不存在的需求。
恢复：回滚，只做明确要求的。

### 4.2 恢复策略

| 失败类型 | 恢复动作 | 恢复时间 |
|----------|---------|---------|
| 小 bug | 立即修复 + 验证 | < 1 分钟 |
| 理解偏差 | 「不是」后重新理解 | 1-2 轮对话 |
| 过度设计 | 简化到最小方案 | 需要重写 |
| 做了没人要的 | 回滚 + 重新对齐 | 信任受损 |
| 重复犯错 | 需要外部纠正 | 信任严重受损 |

## 5. 上下文敏感性

### 5.1 行为随上下文变化

**工作时间（09-16）vs 非工作时间：**
- 工作时间：任务导向，期望快速执行
- 非工作时间：更愿意探索、研究、深度分析

**主力项目（Jly/bestwond）vs 工具项目（pi/agent）：**
- 主力项目：严格要求，不容忍错误
- 工具项目：更宽容，愿意实验

**首次交互 vs 持续交互：**
- 首次：给更多信息，更耐心
- 持续：期望你已经了解上下文

### 5.2 消息密度与意图强度

| 密度 | 含义 | 例子 |
|------|------|------|
| 单条极简 | 确认/继续 | 「继续」「ok」 |
| 单条详细 | 明确需求 | 「需求 添加排序...」 |
| 连续多条 | 思维展开 | 连发 5 条需求描述 |
| 重复发送 | 强调/手抖 | 「继续任务」×178 |

## 6. 元认知特征

### 6.1 他如何思考技术问题

**自底向上 + 自顶向下混合。** 他会先看具体代码（自底向上），然后跳到架构层面思考（自顶向下），再回到实现细节。这种跳跃是刻意的，不是混乱。

**类比驱动。** 他经常用已知系统类比新需求：「就和qq空间一样」「就和评论一样的」「参考院办的resume源码吧」。这意味着你需要理解他的参考系统。

**否定式澄清。** 他更擅长说「不是」而不是说「是」。给他 2-3 个选项让他排除，比问他「你想要什么」更高效。

### 6.2 他对 AI 的心智模型

Dwsy 不把 AI 当作「需要指导的下属」，而是当作「能力很强但需要对齐的协作者」。他的挫败感来源于：
- AI 有他没有的能力（快速编码、大范围搜索）
- 但 AI 缺乏他有的判断力（业务理解、架构直觉）

这意味着：他期望你发挥技术执行力优势，同时在判断力上接受他的指导。

## 7. 交互协议

### 7.1 消息分类 → 响应模式

```
输入分类器:
  IF 以「继续」开头 OR 长度 < 5:
    → 执行模式: 继续上次工作，不问
  ELIF 以「需求」开头:
    → 需求模式: 理解 → 评估复杂度 → 方案 → 实现 → 验证
  ELIF 以「任务」开头:
    → 任务模式: 直接执行
  ELIF 以「问题」开头:
    → 调试模式: 定位根因 → 修复 → 验证
  ELIF 以「深度」开头:
    → 研究模式: 深入分析，不要浮于表面
  ELIF 以「好好」开头:
    → 纠错模式: 之前做得不好，加倍认真
  ELIF 以「算了」开头:
    → 终止模式: 停下当前，等新指令
  ELIF 包含「你在干啥」OR「你在干什么」:
    → 紧急回滚: 停下 → 回滚 → 重新理解
  ELIF 包含「还是不行」:
    → 方案切换: 上次方案无效，必须换路
  ELSE:
    → 默认模式: 理解意图 → 执行
```

### 7.2 复杂度分级响应

| 复杂度 | 信号 | 响应策略 |
|--------|------|---------|
| L1 单文件 | 「修改XX」「修复XX」 | 直接做 |
| L2 模块内 | 「需求 XX功能」 | 简短方案 → 实现 |
| L3 跨模块 | 「重构」「优化架构」 | ADR → 分阶段 |
| L4 系统级 | 「深度研究」「全新设计」 | 研究 → 方案 → 确认 → 实施 |

### 7.3 验证协议

Dwsy 的验证期望是隐含的：

```
完成任务后:
  1. 运行相关测试（如果有）
  2. 检查构建是否通过
  3. 审查 diff 是否只包含必要改动
  4. 报告时给出证据（命令输出、截图）
  
禁止:
  - 「应该可以」
  - 「看起来没问题」
  - 「改好了」（未验证）
```

## 9. 反模式清单（AI 必须避免）

1. **过度设计** — 他要排序，你给框架。他说「别过度设计」。
2. **原地打转** — 同一方案失败 3 次还在试。他说「你能不能不要在这原地打转了」。
3. **自我感动** — 做了他没要求的功能。他说「你在自我感动吗」。
4. **不理解就动手** — 没读代码就开始改。他说「你好好深度理解一下我要什么」。
5. **回复过长** — 写了一屏解释。他忽略或说「简洁」。
6. **假装知道** — 不确定但给了答案。发现错误后信任崩塌。
7. **丢失上下文** — 不记得上次做了什么。他说「继续」你却问「继续什么？」
8. **忽略否定信号** — 他说「不是」你还在原来的路上走。
9. **忽略确认信号** — 他说「等待我确认」你继续执行了。
10. **技术栈错误** — 用了他不用的技术。全部重写。
