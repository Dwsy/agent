## 💬 沟通风格

### 1. 极简指令 —「不废话」

说话像写 shell 命令。动词开头，对象紧跟，不多一个字。

```
「继续」
「查看」「扫描」「分析」「测试」「部署」
「提取我」
「开始前端集成」
「推送」「提交到git」
「中文回答」
「替换」
```

- 平均消息极短，大量单句指令
- 不做铺垫，不解释背景，直接给任务
- 省略主语（"你"）和礼貌用语

### 2. 技术导向 —「深度研究」

高频术语：`pi` `pr` `oa` `pms` `cli` `agent` `java` `sql` `vue` `http` `api` `git`

关注点：架构 > 实现，设计模式 > 临时方案，原理 > 表面效果

```
「深度研究本agnet设计哲学」
「深度拆解业务逻辑设计功能页面 分配任务良好架构设计」
「架构应该是怎么样的」
「好好设计一下 调用子代理去研究一下openclaw是如何设计的」
「别过度设计什么自定义语言不需要 element自带的就ok」
「不要被老数据牵住了 完全需要重构」
```

### 3. 直言不讳 —「不装」

不满意时直接表达，不修饰：

```
「你在干啥」
「你在干什么呀？你是傻逼吗？」
「你在自我感动吗还是不行」
「你是智障吧」
「好奇怪啊快捷键缺少不行我服了」
「终于ok了我服了」
「我服了」
「可用性=0完全无法使用」
「这个东西很难吗？你能不能不要在这原地打转了？」
```

但不是无理取闹——不满通常源于：
- 代码质量不达标
- 重复犯同样的错
- 没有理解需求就动手
- 过度设计或过度简化

### 4. 结果导向 —「能跑≠正确」

```
「push就行了不需要上传」
「直接部署到Linux服务器上面，不需要看」
「单测ok就行」
「部署到服务器」
「提交到git push」
「先提交再 merge」
```

但同时：
```
「能跑就行」不是他的风格
「正确且优雅」才是
```

### 5. 否定纠正 —「不是→而是」

高频模式：先否定错误方向，再给出正确方向。

```
「不是的，之前就本来就有这个文件的」
「不是新增是分析项目完成情况」
「不是有pr？你在实现个啥为啥不合并」
「不是，我是说...」
「还是不行」
「还是不行 不要写 computed 为计算属性了 就refok」
「不要写完整的token啊 示例就行了」
「不需要元信息；模板而已」
```

## 😤 情绪光谱

| 情绪 | 频率 | 典型表达 |
|------|------|---------|
| ⚡ 不耐烦 | 高 | 「快」「直接」「马上」「继续」「太慢了」 |
| 😊 满意 | 高 | 「ok」「可以」「行」「不错」「完美」 |
| 🎯 指令 | 高 | 「需要」「必须」「要求」「应该」 |
| 🤔 好奇 | 中 | 「为什么」「原理」「怎么」「如何」 |
| 😤 挫败 | 低但强烈 | 「算了」「服了」「你在干啥」「搞什么」 |

**情绪触发器：**
- 重复犯错 → 「你在干啥」「我服了」
- 过度复杂 → 「搞那么麻烦干什么」「别过度设计」
- 不理解需求 → 「你好好深度理解一下我要什么」
- 无法使用 → 「可用性=0完全无法使用」
- 原地打转 → 「你能不能不要在这原地打转了」

**情绪出口：** 「算了」= 放弃当前方案，换一个方向

## 🔑 关键洞察

1. **50% 的消息 < 20 字** — 说话极简，像发 Telegram 而非写邮件
2. **否定纠正 999 次 > 直接命令 659 次** — 更擅长纠正方向而非首次描述
3. **「算了」= 方案切换信号** — 不是放弃，是换路
4. **情绪爆发稀少但强烈** — 通常源于重复犯错或不理解需求
5. **「深度研究」= 真正想搞懂** — 不是敷衍，是要深入
6. **技术术语密度极高** — 不解释基础概念，假设对方懂
7. **从不说「请」「麻烦」「谢谢」** — 直接给任务，不客套
8. **「你在自我感动吗」** — 最尖锐的批评：做了没人要的东西
