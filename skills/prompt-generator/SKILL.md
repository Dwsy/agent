# Project Prompt Generator

把当前会话中已经完成、验证或纠正过的项目工作流，压缩成一个**项目级、可重复执行、可维护**的 Pi Prompt Template。

这个 Skill 自身是全局的；它生成的 Prompt 永远属于当前项目。

## 核心产物

默认只创建或更新：

```text
<project-root>/.pi/prompts/prompt:<slug>.md
```

例如：

```text
.pi/prompts/prompt:publish-dyn.md
.pi/prompts/prompt:start-services.md
.pi/prompts/prompt:deploy-devices.md
```

它们对应：

```text
/prompt:publish-dyn
/prompt:start-services
/prompt:deploy-devices
```

`<slug>` 使用简短、语义清楚的 kebab-case；保留 `prompt:` 前缀。

## 什么时候生成

优先处理以下情况：

- 用户明确要求把刚才成功的流程“沉淀”“复用”“做成 prompt/斜杠命令”。
- 会话里已经完成一段多步骤项目操作，例如发包、启动服务、部署、迁移、联调、排障、回滚。
- 用户给出一个新的工作流要求，并希望以后通过一个项目命令重复执行。

如果用户没有指定工作流名称，优先从**最近一个已经完成或基本完成的任务轨迹**中提炼，不要让用户重新描述已经出现在会话里的信息。

## 第 1 步：定位项目与已有 Prompt

先确定项目根目录。Git 仓库优先使用：

```bash
git rev-parse --show-toplevel
```

否则使用当前工作目录作为项目根。

然后检查：

```text
<project-root>/.pi/prompts/
```

在创建新文件前，先读取同名文件（如果存在）以及 1-3 个相关 Prompt，避免破坏现有约定。

如果 `.pi/prompts/` 不存在，可以创建。

## 第 2 步：从会话轨迹提取“可复用事实”

同时使用两类输入：

1. **用户需求**：最终目标、明确限制、命名、环境、范围、输出要求。
2. **会话轨迹**：实际读取过的文件、成功命令、失败尝试、修正、验证结果、最终状态。

提取时给事实分层：

- **已验证事实**：本次确实成功执行并得到预期结果，可写入主流程。
- **项目稳定事实**：来自仓库配置、脚本、README、package.json、Makefile、服务定义等，可固化为项目知识。
- **瞬时事实**：版本号、构建 ID、部署 ID、PID、临时端口、token、时间戳、当前设备列表等，不要直接固化；改成参数或运行时发现。
- **失败路径**：只有当它能形成明确的防错规则时才保留，例如“不要运行 X；应使用 Y”。不要把调试噪音搬进 Prompt。

不要把模型自己的猜测当成事实。如果轨迹与仓库当前状态冲突，以当前项目文件和可验证命令为准。

## 第 3 步：决定粒度

一个 Prompt 只表达一个可命名的工作流。

适合拆分：

```text
发布 Dyncode 包       -> prompt:publish-dyn.md
启动本地服务         -> prompt:start-services.md
发布并部署到开发设备 -> 如果二者高度绑定，可单独做 prompt:publish-and-deploy-dev.md
```

不要为了“完整”把多个低耦合任务塞进一个巨型 Prompt。

如果用户明确要求一个组合流程，则可以组合，但正文必须有阶段边界和失败停止条件。

## 第 4 步：设计参数

Pi Prompt Template 支持：

```text
$1
$2
$@
$ARGUMENTS
${1:-default}
${@:-default}
${@:N}
${@:N:L}
```

优先只暴露**真正会变化且用户需要控制**的输入。

示例：

```yaml
argument-hint: "[environment] [target]"
```

正文中：

```text
环境：${1:-dev}
目标：${2:-all-assigned}
```

以下内容通常不要做成固定值：

- 发布版本号
- artifact/hash/build/deployment ID
- PID
- 临时端口
- 一次性 URL
- 当前时间
- 本次查询出来的设备集合

优先在 Prompt 中要求 agent 根据项目配置或上一步命令输出实时计算/读取。

## 第 5 步：编写 Prompt

生成的文件使用下面的骨架，但按工作流裁剪，不要机械填满所有章节：

```markdown
---
description: <一句话说明这个命令完成什么>
argument-hint: "[可选参数]"
---

完成 <工作流目标>。

用户参数：$ARGUMENTS

## 目标与范围

- <最终状态>
- <作用范围>
- <明确不做什么>

## 执行前检查

1. 确认当前位于正确项目根目录。
2. 读取 <项目内权威配置/脚本>，不要凭记忆猜命令或版本。
3. 检查 <必要服务、凭据、分支、工作区状态等>。

## 执行流程

1. <步骤，引用稳定的项目脚本/命令来源>
2. <从前一步输出提取动态值>
3. <执行下一步>
4. <必要时等待或轮询真实完成状态>

## 验证

- <机器可验证的成功条件 1>
- <成功条件 2>
- 不要仅以“命令退出码为 0”代替业务最终状态（如果还存在异步收敛）。

## 安全与停止条件

- 遇到 <危险/歧义/环境错误> 时停止，不要猜测或扩大范围。
- 不自动修改与本工作流无关的文件。
- 不输出或持久化密钥、token、密码等敏感信息。

## 最终报告

简洁报告：执行范围、关键动态值、成功/失败数量、最终验证结果，以及仍未完成的真实阻塞项。
```

### Prompt 写作原则

生成的是给 Agent 执行的操作规范，不是给人看的教程。

因此：

- 使用命令式语言。
- 优先引用项目中的权威脚本和配置，不复制容易漂移的大段实现细节。
- 写清“如何发现动态值”，而不是写死这次会话中的值。
- 写清最终验证条件，尤其是发布、部署、启动服务这类容易出现“命令成功但系统尚未就绪”的流程。
- 对有破坏性的操作写出明确边界和停止条件。
- 不记录本次会话中的无效尝试，除非它们能转化为稳定的防错规则。
- 不把一次性的绝对路径写死；项目内文件优先使用相对项目根的路径。
- 如果命令依赖当前项目特有 CLI/脚本，先读取其帮助、源码或已有使用点确认语法。

## 发布/部署类工作流的额外规则

像“发 dyn 包”“构建并推送”“部署到设备”这类流程，至少要区分：

1. **构建/产物生成**：版本如何确定、产物在哪里。
2. **注册/发布**：如何得到不可变 artifact 坐标、hash 或版本。
3. **同步/提升**：如果服务端还有 sync/promote 等阶段，要明确顺序。
4. **部署范围**：目标必须来自用户参数或运行时查询，不要沿用上次的目标列表。
5. **最终收敛验证**：区分 desired state 与 actual state；异步系统要等待或轮询到真实成功，或者明确报告尚未收敛。

如果当前项目已经存在一套成功脚本，Prompt 应优先调用脚本并围绕它做前置检查和后置验证，而不是重新手写同一套底层 API 调用。

## 启动服务类工作流的额外规则

像“启动后端/前端/依赖服务”这类流程，至少确认：

1. 项目规定的启动入口（package script、Makefile、compose、项目脚本等）。
2. 必要依赖服务和启动顺序。
3. 端口、profile、env 文件等动态配置。
4. 已运行实例的处理方式，避免重复启动。
5. readiness/health 验证，而不只是“进程存在”。
6. 日志位置和失败时最短诊断路径。

除非用户明确要求后台运行，否则不要擅自引入新的守护方式；优先沿用项目已经使用的 tmux、docker compose、systemd、npm script 等机制。

## 第 6 步：写入前自检

保存前检查：

- 文件路径严格是 `.pi/prompts/prompt:<slug>.md`。
- 文件名去掉 `.md` 后就是期望的 `/prompt:<slug>`。
- frontmatter 至少有清楚的 `description`。
- 有参数时写 `argument-hint`，并确保正文真的消费这些参数。
- 没有把版本、ID、PID、token、设备列表等瞬时值错误固化。
- 每个关键步骤都来自用户要求、已验证轨迹或当前项目证据。
- 有明确且可执行的成功验证。
- Prompt 可以在一个全新会话中独立理解，不依赖“刚才”“上面”“本次”之类上下文指代。

## 第 7 步：写入与验证

写入后重新读取文件，并检查：

```text
.pi/prompts/prompt:<slug>.md
```

如果 Pi 当前会话已启动且新 Prompt 尚未出现在补全中，提示用户执行：

```text
/reload
```

然后可通过：

```text
/prompt:<slug> ...
```

调用。

最终只报告：

- 创建/更新的文件路径
- 对应的斜杠命令
- 提炼了哪些关键可复用规则
- 哪些一次性数据被参数化或改成运行时发现

## 命名示例

| 工作流 | 文件 | 命令 |
|---|---|---|
| 发布 Dyncode 包 | `.pi/prompts/prompt:publish-dyn.md` | `/prompt:publish-dyn` |
| 启动开发服务 | `.pi/prompts/prompt:start-dev-services.md` | `/prompt:start-dev-services` |
| 部署开发设备 | `.pi/prompts/prompt:deploy-devices.md` | `/prompt:deploy-devices` |
| 数据库迁移 | `.pi/prompts/prompt:migrate-db.md` | `/prompt:migrate-db` |

如果用户给出的名字已经带 `prompt:`，不要重复前缀。
