# 统一视觉生成路由与内容编排

> 将 Generative UI 从“Agent 手选 modules/templates 的能力目录”升级为 request-first 的视觉生成编排层：自动选媒介、表示法、风格、内容结构、检索策略和一个最相关 skeleton。

## 背景与目的 (Why)

现有 `visualize_read_me` 要求 Agent 先理解 `runtime/art/mockup/interactive/chart/diagram/canvas` 等实现模块，再自行选择模板。用户虽然能得到可运行 Widget/Canvas，但体验仍割裂：同类需求的视觉风格不稳定、复杂分析容易只有卡片/控件骨架、事实缺失时存在套用 demo 值的风险，而且用户经常需要额外提示“用什么图/什么工具/是否搜索”。

本次目标是让用户只表达问题和目标，Agent 自主完成 `request → route → representation/style/content/research → guidance/template → render`。

## 变更内容概述 (What)

- 新增纯路由层 `routing.ts`：自动决定 `markdown/show_widget/show_canvas`、表示法、视觉风格、minimum content plan 与 retrieval policy。
- 新增纯 planner `visual-plan.ts`：把自然语言 request 与 guidance/template 组合成一次可执行规划；自动模式一次只展开一个最相关 skeleton。
- `visualize_read_me` 改为 `request` 优先；`modules/templates` 变为 optional expert override，不再要求用户或 Agent 手工拼装。
- representation routing 覆盖 text-first、linear/branched flow、architecture/hybrid、timeline/roadmap、comparison、record detail、single/multi chart、evidence brief、diff review、form state、task workflow、UI mockup、interactive explainer、illustration。
- 显式表示法优先于主题词：例如 `compare two architectures` 走 comparison，`architecture migration roadmap` 走 timeline，`workflow between services` 走 flow。
- large architecture 自动采用“small topology overview + grouped detail”内容计划，避免把大量组件挤进单一 graph。
- 新增 `timeline-roadmap` HTML skeleton 与内容丰满的 `canvas-brief` TSX skeleton。
- retrieval policy：current/latest/news/price/weather 等时效请求或显式 search/verify → `required`；其他事实不足 → `if_missing`；明确禁止 template/demo 值替代事实。
- 新增宿主强制 grounding boundary：`show_widget/show_canvas` 每次渲染必须声明 `grounded` 或 `not_applicable`；事实型 artifact 至少一个结构化 source，宿主自动渲染可见 provenance footer 并持久化 declaration。
- Widget 校验从 `tools.ts` 抽为 `widget-validation.ts`，与 Canvas validator 一样拥有直接行为测试；既有 MCP/ngrok inspector 集成测试进入默认 `pnpm test`。
- 统一 Widget/Canvas UI/UX contract：24/18/16/14/12 字阶、4/8/12/16/24/32 spacing rhythm、flat semantic surfaces、host theme tokens、约 320px 窄宽重排与 semantic controls。
- 修正旧的“所有标题/说明都必须放聊天外”规则：纯图不重复 chat prose；自包含 audit/report/evidence brief 必须在 artifact 内包含 scope/evidence/findings/source。
- README 与 `show_widget/show_canvas` prompt guidance 均切换到 request-first 心智模型。
- 新 router/planner 测试已加入默认 `pnpm test`。

## 风险与影响评估 (Risk Assessment)

- Router 采用 deterministic intent rules，不是额外模型调用；优点是稳定、低成本，风险是非常模糊的自然语言仍可能需要 Agent 根据返回的 reason/contentPlan 做最终判断。
- `research` 仍不在 read_me 内部自行联网；Agent 必须使用当前会话实际可用的 search/file/code/data 工具执行检索。渲染边界新增 `grounding` runtime invariant，能强制来源 declaration 与可见 provenance，但不会替代上游工具对“来源内容是否真实”的鉴别。
- `canvas-brief` 和其他 skeleton 包含结构示例数据；route/guidance 多处明确要求在真实 artifact 中全部替换为 supplied/retrieved evidence，事实型渲染若无 provenance source 会在 show-tool execute 前失败。
- Widget/Canvas CSP 继续允许现有 runtime 所需的 `unsafe-inline` / `unsafe-eval`，远端白名单 CDN 也尚未引入 SRI；本次不做高风险 CSP 重构，保留为已知安全权衡。
- manual modules/templates 继续保留；只给已知 template 时 planner 会从 catalog 反推 target/modules，避免高级覆盖需要重复提示。
- 本次建立在同一工作区已经完成的 Cursor-compatible Canvas SDK / Gallery Canvas host 上，但不改变其 runtime 安全边界。

## 详细变更说明

### 1. Request-first representation router

**问题：** modules/templates 是实现细节，不能直接代表用户意图；Agent 需要额外猜媒介和风格。

**方案：** `routeVisualRequest()` 以自然语言请求为输入，输出 route id、target、style、modules、最多一个 template、reason、minimum content plan、research policy。显式 representation（comparison/timeline/flow/illustration）优先于容易冲突的主题词。

**影响范围：** `visualize_read_me` 的默认规划路径；用户无需改变 show tools 的运行时参数。

### 2. Content-first planner 与 autonomous retrieval contract

**问题：** 过去模板提供的是“UI 怎么长”，没有系统规定“artifact 至少应该包含什么证据”。

**方案：** 每条 route 都带 content plan；统一 anatomy 为 `context → dominant artifact → evidence/detail → source/recency → action-if-needed`。时效/显式检索请求标记 `required`，其他缺证据场景标记 `if_missing`，Agent 先检索后 render。show-tool 边界再要求显式 `grounding`：`grounded` 必须携带结构化 source，宿主负责 escape 并生成可见 provenance footer；`not_applicable` 仅用于非事实型产物且必须写明原因。

**影响范围：** Agent 生成策略与 show-tool 参数 schema；不新增网络权限，也不绕过现有工具边界。

### 3. 统一 UI/UX 视觉语言

**问题：** Widget 与 Canvas 的字号、间距与“标题是否应放 artifact 内”等规则存在冲突。

**方案：** 共用 24/18/16/14/12 type scale、4/8/12/16/24/32 spacing rhythm、flat semantic surface、host token color 与窄宽 responsive 规则。纯图保持简洁，自包含分析 artifact 则必须完整承载必要 context/evidence/source。

**影响范围：** guidance/prompt，不改变 Widget/Canvas runtime API。

### 4. 参考 visual-explainer 的边界

参考 `nicobailon/visual-explainer` 的 prepare→render 分层与 representation routing：flow/topology 用 graph、text-heavy architecture 用 grid/hybrid、comparison/audit matrix 用 aligned structure、timeline 用 chronology、metrics 用 charts。

没有复制其 standalone HTML 文件协议、browser opener、palette/font picker 或宿主实现；Pi 继续使用 `show_widget/show_canvas`、host theme tokens、现有 CSP/bridge 与 progressive templates。
