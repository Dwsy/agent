# Issue: 统一视觉生成路由与内容编排

## Goal

让用户只描述问题/目标，Agent 自动决定是否需要可视化、选择正确媒介/表示法/视觉风格、判断是否应先检索事实，并按需加载一个最相关模板，生成内容完整且风格统一的 Widget/Canvas，而不是让用户手动理解 modules/templates。

## 背景/问题

原 `visualize_read_me` 以 `modules + templates` 为入口，属于实现能力目录而不是用户意图路由。功能虽然齐全，但 Agent 必须先自行猜测工具/模块，容易出现“只有 UI 架子、缺真实内容”、同类任务风格不一致、该搜索时直接填示例数字，以及用户需要写过多提示的问题。

## 验收标准 (Acceptance Criteria)

- [x] WHEN 用户仅给出自然语言视觉目标，系统 SHALL 自动返回 `target/style/modules/template/contentPlan/research` 路由结果，不要求用户选择 Canvas/Widget/modules/templates。
- [x] WHEN 请求对应流程、架构、timeline、比较、记录、图表、审计/报告、diff、表单、任务流、UI mockup、交互解释或插画，系统 SHALL 选择对应表示法与最小可用媒介。
- [x] WHEN 请求涉及 current/latest/news/price/weather 等时效性事实或显式要求搜索，系统 SHALL 标记 retrieval 为 required；其他事实不足时 SHALL 标记 if_missing，禁止使用模板示例值替代事实。
- [x] WHERE 自动路由选择模板，系统 SHALL 一次只展开一个最相关 skeleton；手动 modules/templates 仍 SHALL 作为高级 override。
- [x] WHEN 生成 Widget/Canvas，系统 SHALL 遵循统一 typography/spacing/surface/color/responsive/accessibility contract，并包含 context → dominant artifact → evidence/detail → source/recency → action-if-needed 的内容骨架。
- [x] WHEN 渲染任何 Widget/Canvas，系统 SHALL 在宿主边界要求显式 `grounding`；事实型产物 SHALL 至少声明一个结构化 provenance source，并由宿主渲染可见 source/scope footer、持久化 declaration，而不是只依赖 prompt 约束。
- [x] WHEN 请求没有明显视觉收益或显式要求 text-only，系统 SHALL 路由到 Markdown，不为了使用工具而强行创建 UI。
- [x] WHEN 默认复杂视觉请求无法归入更具体类型，系统 SHALL 使用内容丰满的 evidence brief，而不是空 dashboard/card shell。
- [x] WHEN 相关测试执行，系统 SHALL 覆盖路由分类、research policy、模板真实编译、自动 read_me 契约和现有 generative-ui 回归。

## 关键决策

| 决策 | 理由 |
|------|------|
| `request` 成为默认入口，manual modules/templates 仅 override | 用户不应理解实现模块才能得到正确视觉 |
| 自动模式只展开一个模板 | 保持 progressive disclosure，避免把完整模板库塞进上下文 |
| router 可返回 `markdown` | 最小媒介原则；工具存在不代表必须生成 UI |
| research policy 属于 route contract | 内容完整必须建立在真实 evidence 上，不能把示例值当事实 |
| `grounding` 在 show-tool 边界强制校验并由宿主展示 provenance | 把来源要求从“模型应遵守”提升为可验证、可持久化的 runtime invariant |
| 默认复杂请求落 `canvas-brief` | 提供完整的 context/takeaway/evidence/caveat/source 骨架，解决“功能架子没有内容” |
| 借鉴 visual-explainer 表示法路由，不复制其 HTML/browser host | 复用成熟信息架构思想，保持 Pi Widget/Canvas 宿主与主题/安全模型 |
