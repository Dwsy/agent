# Loop 与角色记忆插件 OS 化升级

## Status
Planned

## Background

用户希望先把 `extensions/loop.ts` 从单文件升级为文件夹包形式的 Pi 插件，因为当前 700+ 行单文件可维护性低；同时希望参考图片中的 Matrix Agent Company OS 架构，顺便规划 `extensions/role-persona-old/` 的升级。

已确认真实上下文：

- `extensions/loop.ts` 是 700+ 行单文件扩展，已有 `/loop self/debug/tdd/review/verify/tests/plan/custom/stop` 等模式。
- 当前 `extensions/loop.ts` 有未提交本地修改（约 +90/-16），迁移时必须保留。
- `extensions/goal/` 已是目录包形式，可作为 Pi 扩展模块化参考。
- `extensions/role-persona-old/` 是 2500+ 行 `index.ts` 编排层 + 多个记忆/知识模块，已有分层记忆、pending、vector、knowledge、skills。
- 图片架构核心是：Workspace Brain → Runtime Command Plane → Department Verticals → Lead Agents → Worker Pool → Proof Loop → Memory/Skill Update。

## Goal

把 Loop 与 Role Persona 两个插件演进为 Pi 内部的轻量 Agent Company OS 基座：

1. `loop` 负责 Runtime Orchestrator、Worker Dispatch、Proof/Check-in Loop。
2. `role-persona-old` 负责 Workspace Brain、Memory/Skill Overlay、部门/角色上下文边界。
3. 两者通过结构化 state/proof/check-in/memory-update 协作，而不是互相硬耦合。

## Non-Goals

- 不在第一阶段重写 loop 行为。
- 不在第一阶段合并 `/loop` 与 `/goal`。
- 不在第一阶段引入真实多部门自动调度。
- 不自动写长期记忆，除非 proof/check-in 已验证且用户确认策略。
- 不做高权限自动操作（删除、发布、付款、外部提交）。

## Architecture Mapping

| Matrix OS 概念 | Pi 插件映射 | 当前状态 | 升级方向 |
|---|---|---|---|
| Workspace Brain | `role-persona-old` core/context/memory/knowledge | 已有 | 增加 workspace profile + loop policy |
| Memory/Skill System | role memory + role/global/project knowledge + skills | 已有 | 增加 loop outcome 到 memory/knowledge 的晋升规则 |
| Runtime Command Plane | `loop` + `goal` | 部分已有 | `loop/` 模块化 + loop state/proof ledger |
| Department Verticals | role/department profiles | 未结构化 | 以配置/模板定义 engineering/research/writing/review |
| Department Lead Agent | loop preset controller prompt | 雏形 | 每个 loop spec 绑定 lead prompt + memory scope |
| Worker Pool | native pi/subagent/herdr/browser | 部分可用 | 统一 worker seat 描述，先不做自动执行 |
| Proof Loop | loop verify/signal | 太弱 | proof ledger + checker gate |
| Memory Skill Update | auto-memory/pending/knowledge | 已有 | 只从 verified check-in 生成候选记忆 |

## Phase 1 — Loop 单文件迁移为目录包

### Scope

只做结构迁移，行为不变。

### Target Structure

```text
extensions/loop/
├── index.ts          # default export，注册命令/工具/事件
├── types.ts          # LoopMode / LoopTask / LoopStateData
├── constants.ts      # LOOP_STATE_ENTRY / HAIKU_MODEL_ID / presets
├── prompts.ts        # buildPrompt / getCompactionInstructions
├── summary.ts        # SUMMARY_SYSTEM_PROMPT / summarize*
├── state.ts          # get/set/clear loop state
├── ui.ts             # widget/status rendering
├── tools.ts          # submit_loop_plan / signal_loop_success
├── commands.ts       # /loop command parsing
├── events.ts         # agent_end/session_before_compact handlers
├── tsconfig.json     # local typecheck config, same style as goal
└── typings/          # if needed, reuse/copy goal typings
```

### Acceptance Criteria

- [ ] `extensions/loop/index.ts` exports default extension function.
- [ ] `/loop` command behavior matches old `loop.ts`.
- [ ] `submit_loop_plan` and `signal_loop_success` tool names unchanged.
- [ ] `agent_end` continuation behavior unchanged.
- [ ] `session_before_compact` loop instructions unchanged.
- [ ] Existing local edits in `extensions/loop.ts` are preserved in new modules.
- [ ] Old `extensions/loop.ts` is removed or moved so Pi does not double-load.
- [ ] Typecheck or equivalent import/load check passes.

### Risk Controls

- Before edits, inspect `git diff -- extensions/loop.ts` and migrate from working tree content, not HEAD.
- Use exact copy/split first; no functional refactor during migration.
- Verify no duplicate command/tool registration.

## Phase 2 — Loop Safety Controls

### Scope

Add minimal hard stops and runtime visibility.

### Features

- `/loop status`
- `/loop pause`
- `/loop resume`
- `/loop stop` remains/gets clearer
- `--max <n>` maximum iterations
- `--timeout <duration>` optional wall-clock cap
- repeated-stuck detection: same failure/summary repeated twice → stop/block
- widget shows mode, iteration, status, stop reason

### Acceptance Criteria

- [ ] Loop stops when max iteration reached.
- [ ] Pause prevents next continuation injection.
- [ ] Resume restores continuation injection.
- [ ] Status reads persisted state, not in-memory only.
- [ ] Stop reason persisted in session entries.

## Phase 3 — Proof Ledger

### Scope

Replace loose success signal with evidence-first completion while keeping backwards compatibility.

### Proposed Tool

```ts
submit_loop_proof({
  status: "passed" | "failed" | "blocked",
  artifacts: string[],
  checks: Array<{
    name: string,
    command?: string,
    exitCode?: number,
    summary: string
  }>,
  diffSummary?: string,
  risks: string[],
  nextStep?: string
})
```

### Behavior

- `signal_loop_success` can remain as deprecated alias for simple loops.
- Proof entry persisted as `loop-proof` session entry.
- Loop only auto-completes when proof status is `passed` and required checks exist.
- `/loop proof` shows latest proof.

### Acceptance Criteria

- [ ] No proof → no final success for verification/code loops.
- [ ] Proof survives compaction.
- [ ] Failed/blocked proof leads to next iteration or stops with reason.
- [ ] User can inspect proof ledger.

## Phase 4 — Loop Spec Templates

### Scope

Turn repeated loop rules into reusable specs.

### Target Structure

```text
~/.pi/agent/loops/
├── coding-fix.yaml
├── tdd.yaml
├── review.yaml
├── verify.yaml
├── llm-wiki.yaml
└── research.yaml
```

### Spec Shape

```yaml
name: coding-fix
goal: "修复指定问题并验证"
input:
  allowed_paths: []
  readonly_paths: []
lead:
  prompt: "工程部门主管：先定位真实代码，再做最小改动"
worker:
  seat: native
verify:
  commands: []
proof:
  required: [diff_summary, command_output, risks]
stop:
  max_iterations: 6
  repeated_failure: 2
feedback:
  failing_test: "修复单个最高影响失败"
  unclear_requirement: "暂停并询问用户"
```

### Acceptance Criteria

- [ ] `/loop spec list`
- [ ] `/loop run <spec> <goal>`
- [ ] Missing/invalid spec gives clear error.
- [ ] Built-in specs can be extended by user specs.

## Phase 5 — Role Persona OS Upgrade

### Scope

Do not rewrite memory engine. Add structured concepts around workspace brain, departments, loop policy, proof-to-memory pipeline.

### Target Additions

```text
~/.pi/roles/<role>/
├── context/
│   ├── workspace-brain.md      # product/codebase/rules/goals/taste summary
│   ├── departments.md          # department profiles and owners
│   └── loop-policy.md          # proof/check-in/memory rules
├── skills/
│   └── loop-specs.md           # allowed/recommended loop templates
└── memory/
    └── checkins.md             # verified loop outcomes, not raw task spam
```

### New Commands/Tools

- `/role brain` — show active workspace brain summary.
- `/role departments` — list configured department profiles.
- `role_checkin` tool — append verified loop outcome to role check-in log.
- `memory({ action: "promote_checkin" })` — promote verified repeated patterns to pending/consolidated/knowledge.

### Memory Policy

- Raw loop progress stays out of long-term memory.
- Verified proof/check-in can enter `memory/checkins.md`.
- Repeated check-ins can become pending learning.
- Stable reusable process can promote to role/global/project knowledge.

### Acceptance Criteria

- [ ] Role prompt injection can include `workspace-brain.md` and `loop-policy.md`.
- [ ] Loop proof can be referenced by role check-in without tight import coupling.
- [ ] Auto-memory extraction filters task-completion noise from loop chatter.
- [ ] Promotion path is explicit and auditable.

## Phase 6 — Department / Worker Model

### Scope

Add configuration first, automation later.

### Department Profile

```yaml
name: engineering
memory_scope:
  include: [core/constraints.md, context/workspace-brain.md, memory/consolidated.md]
allowed_workers:
  - native-pi
  - subagent-explore
  - subagent-review
proof_required:
  - tests_or_typecheck
  - diff_summary
  - risk_note
```

### Acceptance Criteria

- [ ] Loop can print which department profile it is using.
- [ ] Department profile affects prompt/context/proof requirements.
- [ ] No external worker is launched automatically without explicit user request.

## Implementation Order

1. **P0: loop.ts → loop/ package**
   - Foundation. No behavior change.
2. **P1: loop state commands + hard stops**
   - Prevent runaway loops.
3. **P2: proof ledger**
   - Make work count only with evidence.
4. **P3: loop specs**
   - Reuse patterns, reduce long prompts.
5. **P4: role-persona workspace brain + check-ins**
   - Turn proof into memory safely.
6. **P5: department profiles + worker seats**
   - Matrix-like OS shape.

## Verification Plan

For each phase:

- Run focused TypeScript check for changed extension if available.
- Run a load/import smoke test where possible.
- Use `/reload` manually if needed after code change.
- Run command smoke checks:
  - `/loop status`
  - `/loop verify --max 1`
  - memory/role commands touched by phase
- Inspect `git diff` to confirm surgical changes.

## Open Questions

1. Should `loop` and `goal` eventually share a `LoopEngine`, or stay separate with protocol-level integration?
2. Should proof ledger live only in session entries, or also mirror to role `memory/checkins.md`?
3. Should department profiles be per-role files or global built-in presets?
4. How strict should memory promotion be: user-confirmed only, or repeated-proof auto-pending?
5. Should old `signal_loop_success` remain forever for simple non-code loops?

## Notes

- 图片的关键不是“更多工具”，而是边界、职责、证明、记忆回写。
- 最先要解决的是可维护性和可验证性，不是复杂自动调度。
- `role-persona-old` 已经很强，升级重点是让它成为 loop 的 Brain/Memory 层，而不是把 loop 逻辑塞进去。
